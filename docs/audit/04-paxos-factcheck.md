1. **P0-1（图与正文、图与源三者冲突：广播的主体写错）**

   **写在 `proposer(v)` 里面**。

2. **P0-2（例证挂错了规则：讲义的 A 序列被安到了 n_p=n 这条规则名下）**
   正文 L130 说「少了它（= 收到 accept 时把 n_p 抬到 n），就会出现这样的序列：S1 收 p1、p2、a1(A)；S2 收 p1、p2、a1(A)、a2(B)；
   S3 收 p1、p2、a2(B)：A 曾被 S1 与 S2 接受过，却被 B 覆盖」。
   **但这条序列在讲义里（L259–264）是"为什么 accept 要检查 `n ≥ n_p`"的反例**，而讲义给"为什么要把 n_p 抬到 n"的反例
   是另一条（L269–273：`S1: p1 a2B a1A p3 a3A` / `S2: p1 p2 p3 a3A` / `S3: p2 a2B`，B 曾定案又被 A 覆盖）。
   **我把两种"只去掉一条规则"的情形都演算了一遍**：
   - 只去掉 `n_p = n`（保留 `n ≥ n_p`）：S1 收到 p2 后 n_p=2，随后 a1(A) 因 `1 ≥ 2` 不成立**被拒绝**；S2 同理拒绝 A；
     最终只有 B 被 S2/S3 接受 ⇒ **A 从未被接受**，页面写的"A 曾被 S1 与 S2 接受过"**不会发生**。
   - 只去掉 `n ≥ n_p`（保留 `n_p = n`）：正是讲义 L259–264 的情形 ⇒ A 被接受、随后被 B 覆盖 ✅。
   - 讲义 L269–273 的情形要出问题，靠的是"**accept 没经过 prepare 就直接到达**（S1 收到 a2B 却不曾 p2）"，
     而这恰好就是页面 L130 上半句自己给的理由。
   ⇒ 页面的**理由对、序列挂错**；而这个理由（accept 可能绕过 prepare）对应的正是讲义 L269–273 那条序列。
   → **修在**（二选一，推荐第一种）：
   - ① 把 L130 的序列换成讲义 L269–273 的那条（`S1: p1 → a2B → a1A → p3 → a3A`；`S2: p1 → p2 → p3 → a3A`；`S3: p2 → a2B` ⇒ B 曾定案又被 A 覆盖），
     并把讲义 L259–264 的序列挪到 **L128**（讲 `n ≥ n_p` 那一处），两处各就各位；
   - ② 若不想动 L128，则把 L130 的措辞改成"如果连 `n ≥ n_p` 这道门槛也没有，就会出现……"，并说明这条例外是**两道门槛共同**兜住的。
